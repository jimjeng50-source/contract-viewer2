# 廠商異議回覆台（deviation-reply）

單檔 HTML 工具：把廠商的商務異議檔（Excel／Word／PDF／掃描檔）拖進來 → Gemini 依已累積的規則（沒有規則檔時以買方一般立場）草擬回覆 → 使用者逐項同意或給意見 → 意見萃取成規則（寫入規則檔「提案區」，待主管每月 review 核定）→ 產出完稿（與來源同格式；PDF／掃描轉 Excel 澄清表）。

與本 repo 的合約審查單機版是**不同工具**（審自家合約 vs. 回覆廠商異議），只是放在同一 repo 管理。

## 學習迴路
- **不需事先準備規則檔**：規則檔是使用後歸納的產出。沒有規則檔時，意見歸納出的規則存成本機「新條款（待核）」，按「建立規則檔」產生 Excel（說明／條款庫／提案區／回覆紀錄／詞庫／變更紀錄），放 SharePoint 共用；已有規則檔則按「開啟既有規則檔」。
- 對既有條款的新規則寫入提案區（待核）；規則庫沒有的條款則新增到條款庫（狀態「待核」）並在提案區登記「新增條款」。
- 使用者意見 → AI 改寫回覆，並判斷能否一般化成規則（底線三級或慣用回覆）→ 使用者按「記住」才寫入。
- 規則先存本機，按「存回規則檔」合併進 SharePoint 上的 MasterFile（提案區／回覆紀錄／詞庫，以 ID 去重、保留格式）。
- 之後的草擬會帶入：已核定底線＋所有待核規則（標示待核但優先遵循）＋該條款最近 3 筆實際回覆。
- 每月 Review 匯出差異表與 clean-orange-deck 簡報；主管在提案區填「決議／決議日」即轉正。

## 制式條款參考（src/reference.js）
- 16 個主題分 5 群組（期限／金額上限／保證與款項／責任與保固／契約變動與爭議），每個主題並列 FIDIC 2017 紅皮書、銀皮書、工程會工程／財物採購契約範本、中鼎 PO 慣例的摘要與來源。
- AI 判斷優先序：使用者新規則 > 內部底線 > 中鼎慣例 > 工程會範本 > FIDIC；制式條款**只供內部判斷**，回覆不提出處（使用者 2026-10-19 決定）。
- 立場為「有條件接受」時，AI 另給比照制式寫法的「建議修正條文」（中英），完稿多一欄（Word 附在回覆格內）。
- 學到的規則依主題歸類（條款庫「類別」＝群組、條款名稱＝主題名稱）。
- 規則檔有「制式條款參考」工作表，可修正或貼上正式原文，工具以規則檔為準。FIDIC 欄只放摘要（原文受著作權保護）；標【待查證】者是未能取得該版本原文核對的項目（工程會網站與部分政府網站拒絕自動擷取）。

## 機密處理
- 文字一律以 deid.js 遮蔽（人名、公司、專案、金額、郵址、電話、編號、準則＋詞庫），首次送出必經逐字確認；意見調整若出現新機密詞也會再確認。
- 「讓 AI 參考內部底線」預設開啟（底線會送到 Gemini 免費層）；可在設定關閉，關閉後 AI 只依立場與範例回覆。
- 回覆中出現底線數字而廠商原文沒有 → 標示「可能洩漏底線」。
- 掃描影像無法遮蔽，介面明確警告。

## 開發
```bash
npm install
node tests/engine.test.js      # 引擎單元測試（Node＋xmldom）
python3 build.py               # → dist/廠商異議回覆台.html（約 5 MB，完全離線）
node e2e/run.js                # Playwright e2e（先把 dist 複製成 e2e/app.html、fixtures 複製到 e2e/；mock Gemini）
```
src/deid.js、src/core.js 沿用自 2026-10 的「條款回覆工作台」。
