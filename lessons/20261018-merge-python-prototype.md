# 從 contract-reviewer（Python 原型）併入時只取「規則」不取程式：它的檢查是照大陸「采购合同」通用章節與關鍵字寫的，判定邏輯也有矛盾，直接搬會在中鼎範本上大量誤報。

## 情境

2026-10 使用者決定兩套審查工具併成一套，以本 repo 單機版為主體。contract-reviewer 的 Python 原型（數字／章節／條款三層檢查、OCR）以簡體「采购合同」為範例：
必要章節是「合同標的、單價總價、交付、質量、支付、違約」，高風險詞是「无限责任、单方终止、全额赔偿、知识产权、保密」等。
用其範例合約實跑，報告同時寫「無風險」與「8 處高風險表述」，風險判定本身有矛盾。

## 做法

- 章節完整性：改對準中鼎 PO(C) A～N 條款；既有規則已涵蓋的不重複，只補 A 訂購文件、F 包裝運送、H 催貨、J 取消費四條 `required`（severity: info）。I 高階經理人、L、M 條款意義未確認，**未**建規則，待使用者提供範本再補。
- 高風險措辭：只保留從我方（買方）角度確實有害的「概括免責」「排除保固」兩條 `forbidden`。「單方終止」「知識產權」「保密」在中鼎 PO 是我方標準條款或中性詞，轉入會變成必然誤報，刻意捨棄。
- OCR：不內嵌（tesseract.js＋中文語言檔約 +20MB、辨識率普通），改為掃描檔經使用者確認後送 Claude 辨識文字，再走同一套本機規則與摘要（`aiTranscribeAndReview`）。影像無法去識別化，介面強制勾選確認。
- 承攬契約的章節完整性尚未做（無範本）。

## 為什麼重要

兩套工具名稱、功能清單看起來互補，容易以為「把 Python 版的檢查都搬過來」就更完整。實際上它的前提（大陸通用合同、關鍵字即風險）與本工具（中鼎範本、語意判讀）不相容。之後若再有人想從 contract-reviewer 補功能，先看這份，避免把誤報源帶回來。
